# ユーティリティおよびサポートサービス — 要件


## グローバル前提条件

- すべての操作には有効な入力データおよび適切な権限が必要である。
- 処理上の制約およびスケジューリングの依存関係については、Job Dependencies セクションに記載されている。


## 1. 日付形式の変換および検証
バッチ運用チームとして、私は日付値をセパレータなし形式とハイフン区切り形式との間で変換したい。それにより、後続処理が必要な表現形式で日付を受け取り、また無効な要求が明確に識別されるようにする。

### 要件

REQ-F-001: [イベント駆動] 入力タイプ指示子を受信したとき、システムは、指示子が '1' の場合はセパレータなしの日付（YYYYMMDD 形式）を処理するハンドラへ、指示子が '2' の場合はハイフン付きの日付（YYYY-MM-DD 形式）を処理するハンドラへルーティングし、指示子が '1' でも '2' でもない場合はエラーハンドラへルーティングしなければならない。

REQ-F-002: [望ましくない事象] 入力タイプ指示子が '1' でも '2' でもない場合、システムはエラーメッセージフィールドに 'INVALID INPUT' を設定しなければならない。

REQ-F-003: [望ましくない事象] 出力タイプ指示子が入力タイプと互換性がない場合、システムはエラーメッセージフィールドに 'INVALID INPUT' を設定しなければならない。

REQ-F-004: [普遍的] システムは、処理完了時に呼び出し元のコンテキストを復元し、リターンコードをゼロに設定し、呼び出し元に制御を返さなければならない。

## 2. 待機時間サービスの呼び出し
バッチ運用チームとして、私は制御された実行一時停止機能を持ちたい。それにより、バッチ処理の調整において指定された期間のタイムド遅延を導入できるようにする。

### 要件

REQ-F-005: [普遍的] システムは、標準入力から8文字の待機時間パラメータを受け取り、待機時間サービスに渡すための内部待機時間値として格納しなければならない。

REQ-F-006: [普遍的] システムは、内部待機時間値を渡して待機時間サービスに処理を委譲し、指定された期間だけ実行を一時停止しなければならない。待機時間値はミリ秒として解釈される。

REQ-F-007: [普遍的] 待機時間サービスは、呼び出し元のパラメータ域から遅延間隔値を取得し、タイマーイベント制御ブロックに格納し、インターバル制御タイマーを呼び出して、その期間だけ実行を中断させなければならない。

REQ-F-008: [普遍的] インターバル制御タイマーが満了したとき、システムは呼び出し元の実行コンテキストを復元し、成功のリターンコードとともに呼び出し元に制御を返さなければならない。

## 3. メッセージキューによる日時要求・応答サービス
バッチ運用チームとして、私はメッセージキューから受信した日時要求を処理し、現在のシステム日時で応答したい。それにより、要求元サービスがオンデマンドで正確かつ整形された日時情報を受け取れるようにする。

**再起動／リカバリ:** 3つのキュー（入力、出力、エラー）はメッセージ処理開始前にすべてオープンされる。終了時には、各キューは正常にオープンされていた場合にのみクローズされる。いずれかのキュー操作またはメッセージ操作が失敗した場合、エラー詳細はエラーキューへ送信される。

### 要件

REQ-F-009: [イベント駆動] 入力キューのオープン操作が開始されたとき、システムは、共有入力アクセスおよびコンテキスト保存オプションを指定して入力キューをオープンしなければならない。成功時にはキューハンドルを格納し、REPLY-QUEUE-OPEN フラグを設定する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'INP MQOPEN ERR' を記録する。

REQ-F-010: [イベント駆動] 出力キューのオープン操作が開始されたとき、システムは、put アクセスおよびコンテキスト引渡しオプションを指定して出力キューをオープンしなければならない。成功時にはキューハンドルを格納し、RESP-QUEUE-OPEN フラグを設定する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'OUT MQOPEN ERR' を記録する。

REQ-F-011: [イベント駆動] エラーキューのオープン操作が開始されたとき、システムは、put アクセスおよびコンテキスト引渡しオプションを指定してエラーキューをオープンし、エラーキュー名を 'CARD.DEMO.ERROR' に設定しなければならない。成功時にはキューハンドルを格納し、ERR-QUEUE-OPEN フラグを設定する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'ERR MQOPEN ERR' を記録する。

REQ-F-012: [状態駆動] 入力キューにメッセージが残っている間（NO-MORE-MSGS フラグが設定されていない間）、システムは、NO-MORE-MSGS フラグが設定されるまでメッセージの取得、処理、応答を繰り返し実行しなければならない。

REQ-F-013: [状態駆動] 入力キューにメッセージが残っている間、システムは、5秒の待機間隔で入力キューから次のメッセージを取得しなければならない。成功時には、メッセージID、相関ID、応答先キュー名を抽出し、応答のために保存し、メッセージバッファを要求メッセージ域に移動する。メッセージがこれ以上存在しない場合（理由コード 2033）には NO-MORE-MSGS フラグを設定する。その他の失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'INP MQGET ERR:' を記録する。

REQ-F-014: [普遍的] システムは、現在のシステム日時を取得し、日付を MM/DD/YYYY 形式、時刻を HH:MM:SS 形式でフォーマットし、'SYSTEM DATE : ' に続けて整形済みの日付、'SYSTEM TIME : ' に続けて整形済みの時刻を含む応答メッセージを構築しなければならない。

REQ-F-015: [イベント駆動] 応答メッセージの送信準備が完了したとき、システムは、保存されたメッセージIDおよび相関IDを使用し、文字列形式およびキューマネージャー文字セットを用いて、応答メッセージを出力キューへ送信しなければならない。成功時には条件コードおよび理由コードを記録する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'MQPUT ERR' を記録する。

REQ-F-016: [イベント駆動] エラー状態が検出されたとき、システムは、文字列形式およびキューマネージャー文字セットを用いて、エラー詳細（段落名、返却メッセージ、条件コード、理由コード、キュー名）を含むエラーメッセージをエラーキューへ送信しなければならない。成功時には条件コードおよび理由コードを記録する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'MQPUT ERR' を記録する。

REQ-F-017: [普遍的] システムは、REPLY-QUEUE-OPEN フラグが設定されている場合は入力キューをクローズし、RESP-QUEUE-OPEN フラグが設定されている場合は出力キューをクローズし、ERR-QUEUE-OPEN フラグが設定されている場合はエラーキューをクローズしなければならない。

REQ-F-018: [イベント駆動] 入力キューのクローズ操作が開始されたとき、システムは、格納された入力キューハンドルを使用して入力キューをクローズしなければならない。成功時には条件コードおよび理由コードを記録する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'MQCLOSE ERR' を記録する。

REQ-F-019: [イベント駆動] 出力キューのクローズ操作が開始されたとき、システムは、格納された出力キューハンドルを使用して出力キューをクローズしなければならない。成功時には条件コードおよび理由コードを記録する。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'MQCLOSE ERR' を記録する。

REQ-F-020: [イベント駆動] エラーキューのクローズ操作が開始されたとき、システムは、格納されたエラーキューハンドルを使用してエラーキューをクローズしなければならない。失敗時には条件コードおよび理由コードを取得し、エラーメッセージ 'MQCLOSE ERR' を記録する。


### 未解決の課題

OQ-001: noise_context ルールによれば、応答キュー名は初期化時に 'CARD.DEMO.REPLY.DATE' としてハードコードされている一方、出力キューは各受信要求メッセージから抽出された応答先キュー名に由来するキューハンドルを使用してオープンされる。要求に応答先キュー名が存在しない場合のデフォルトとしてこのハードコードされた応答キュー名を用いるのか、それとも別の目的があるのか。 — 担当: インテグレーション／メッセージングチーム

## 4. 日付検証および Lillian 変換
バッチ運用チームとして、私は日付文字列を検証し Lillian 形式へ変換したい。それにより、呼び出し元が、指定された日付が有効かどうか、また無効な場合はその失敗の性質を記述する構造化された結果を受け取れるようにする。

### 要件

REQ-F-021: [普遍的] システムは、入力日付文字列、日付構造を指定する形式マスク、および呼び出し元からの結果域を、日付検証ワークフローへの入力として受け取らなければならない。

REQ-F-022: [普遍的] システムは、日付変換サービスに処理を委譲して入力日付文字列を Lillian 形式へ変換し、提供された形式マスクに対して検証を行い、その後、返却されたフィードバック構造から重大度コードおよびメッセージ番号を抽出してメッセージレコードに格納しなければならない。

REQ-F-023: [イベント駆動] 日付変換サービスが検証結果を示すフィードバックコードを返したとき、システムは、以下の対応表に従ってフィードバックコードを結果記述にマッピングしなければならない: 無効日付条件は `'Date is valid'` にマッピングされる。データ不足条件は `'Insufficient'` にマッピングされる。不正日付値条件は `'Datevalue error'` にマッピングされる。無効な紀元条件は `'Invalid Era'` にマッピングされる。サポート対象外の範囲条件は `'Unsupp. Range'` にマッピングされる。無効な月条件は `'Invalid month'` にマッピングされる。不正な picture 文字列条件は `'Bad Pic String'` にマッピングされる。非数値データ条件は `'Nonnumeric data'` にマッピングされる。紀元内西暦ゼロ条件は `'YearInEra is 0'` にマッピングされる。その他のフィードバックコードはすべて `'Date is invalid'` にマッピングされる。

REQ-F-024: [普遍的] システムは、検証結果の記述、重大度コード、メッセージ番号、テスト対象日付、および形式マスクを含む整形済みメッセージレコードを、結果域を介して呼び出し元に返さなければならない。


### 未解決の課題

OQ-002: ルール 9134afe8 は、無効日付フィードバックコードを結果記述 `'Date is valid'` にマッピングしている。これは直感に反するように見える — 「無効日付条件」が「日付は有効」というメッセージを生成することは、元資料における名称の逆転である可能性がある。このマッピングが意図的なものか、あるいは条件ラベルと結果記述が入れ替わっているのかを確認すること。 — 担当: 業務／ドメイン有識者

## 5. リモートサーバーへの FTP ファイル転送
バッチ運用チームとして、私は指定されたメインフレームデータセットをリモート FTP サーバーへ転送したい。それにより、そのファイルがリモートシステム上で後続の利用に供されるようにする。

### 要件

REQ-F-025: [普遍的] システムは、提供された認証情報を用いてアドレス 172.31.21.124 のリモートサーバーへ接続し、リモートサーバー上の /ftpfolder ディレクトリへ移動し、ソースデータセットを welcome.txt としてリモートシステムへアップロードし、完了時に接続をクローズする FTP セッションを実行しなければならない。


### 未解決の課題

OQ-003: このルールは、ハードコードされたリモートサーバーアドレス（172.31.21.124）、認証情報（carddemousr / ftpdemo1）、リモートディレクトリ（/ftpfolder）、および対象ファイル名（welcome.txt）を規定している。これらの値のいずれかを、環境固有のデプロイメントをサポートするために設定パラメータとして外部化すべきか。 — 担当: インテグレーション／運用チーム

OQ-004: このルールは、エラー処理の動作（接続失敗、認証失敗、アップロード失敗など）について記述していない。モダナイズされた実装では、リトライロジックまたは失敗通知を定義すべきか。 — 担当: インテグレーション／運用チーム

## 6. インターバルタイマーによる遅延実行
バッチ運用チームとして、私は呼び出し元が指定した間隔だけバッチ実行を一時停止する再利用可能な遅延ユーティリティを持ちたい。それにより、バッチ処理の調整において操作間に制御された待機期間を導入できるようにする。

### 要件

REQ-F-026: [普遍的] システムは、呼び出し元のパラメータ域から遅延間隔値を受け取り、一時停止操作で使用するためにタイマーイベント制御ブロックへ格納しなければならない。

REQ-F-027: [イベント駆動] 遅延間隔値がタイマーイベント制御ブロックへロードされたとき、システムは、その間隔で指定された期間だけ実行を一時停止し、その間隔が満了した後にのみ処理を再開しなければならない。

REQ-F-028: [イベント駆動] タイマー間隔が完了したとき、システムは、呼び出し元のレジスタを復元し、リターンコードを成功に設定し、呼び出し元に制御を返さなければならない。

## 8. 時間ベースのシーケンシング用バッチ処理一時停止
バッチ運用チームとして、私はバッチジョブストリーム内で利用可能な設定可能な待機ステップを持ちたい。それにより、依存するバッチステップを制御された時間ベースの間隔でシーケンス化できるようにする。

### 要件

REQ-F-030: [普遍的] システムは、制御入力から待機時間の長さを受け取り、指定された期間だけバッチ実行を中断しなければならない。この期間はセンチ秒単位で表される（3600 センチ秒 = 36 秒）。

REQ-F-031: [普遍的] システムは、受け取った待機時間値をパラメータとして渡し、一時停止操作を待機時間サービスへ委譲しなければならない。それにより、処理が継続する前に指定された期間だけ実行が中断されるようにする。
